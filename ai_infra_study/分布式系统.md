# **数据并行（DP/DDP）**
每卡完整模型，切分数据，AllReduce 同步梯度——解决”训练时间太长**”
## DP
![[Pasted image 20261027095311.png]]
### 缺点
| ❌ 缺陷       | 📝 原因                                            |
| ---------- | ------------------------------------------------ |
| **GIL 限制** | 单进程多线程，Python 全局解释器锁让多线程无法真正并行调度，CPU 侧成为瓶颈       |
| **负载不均**   | 主卡额外承担 Scatter/Gather、loss 计算、梯度汇总，显存和算力压力都比其他卡大 |
| **通信低效**   | 每步都要重新复制模型；数据走主卡中转，容易挤在 PCIe 上而非高速的 NVLink       |
## DDP
**每块 GPU 一个独立进程**，各进程持有自己的完整模型副本，彼此地位对等——没有”主卡”，梯度同步走**去中心化的 AllReduce**。
1. **初始化**：构造 DDP 时，把 rank 0 的参数 **Broadcast** 到所有进程，保证所有副本起点完全一致
2. **前向 + 反向**：每个进程在自己的数据分片上**独立**计算，互不通信
3. **梯度同步**：反向传播过程中，通过 **AllReduce** 把各进程的梯度取平均，同步后各卡梯度一致
4. **参数更新**：各进程用一致的梯度独立更新——因为起点一致、梯度一致，更新后依然一致

### 核心底层
```python
- **通信重叠（Bucketing）**：为了效率，DDP不会等所有梯度算完才开始一次巨大的AllReduce。它会把梯度**分桶（Bucket）**，当一个桶被填满（或反向传播快结束时），就立刻对这个桶内的梯度发起异步的AllReduce通信。这样，**通信和后续层的反向计算可以并行**，从而隐藏通信延迟。

# 桶根据容量装入参数 桶内梯度计算完毕后，就进行All_reduce通信
塞 L4：桶0 = {L4}，10MB
塞 L3：10+20=30 > 25 → 开桶1，桶1 = {L3}，20MB
塞 L2：20+8=28 > 25 → 开桶2，桶2 = {L2}，8MB
塞 L1：8+12=20 ≤ 25 → 塞进桶2，桶2 = {L2, L1}，20MB
```

## FSDP
**把参数、梯度、优化器状态都切成 NN 份，每卡只存 1NN1​，需要用的时候再临时拼出来**。

![[Pasted image 20261027101325.png]]

- **前向传播前（Pre-forward hook）**：在模块执行前向计算**之前**，触发`All-Gather`，从所有GPU上收集该模块的完整参数。
    
- **前向传播后（Post-forward hook）**：在前向计算**结束后**，立即释放刚刚聚合的、非本GPU持有的参数分片，**只保留自己负责的那一小块**，从而节省显存。
    
- **反向传播前（Pre-backward hook）**：与正向类似，在反向计算开始前，**再次**触发`All-Gather`来重建完整参数。
    
- **反向传播后（Post-backward hook）**：反向计算完成后，释放参数，并触发`Reduce-Scatter`，将梯度规约并分散，每个GPU只保留自己负责的那份梯度分片。

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP,ShardingStrategy 
#初始化钩子函数，挂载到前向 反向过程之中

model=FSDP(model,sharding_strategy=ShardingStrategy.SHARD_GRAD_OP,device_id=local_rank)
=============================
#ShardingStrategy.FULL_SHARD   参数 梯度 优化器 16B
前向之前 all-gather，前向后 reshard；反向前再 all-gather，反向后 reduce-scatter 并 reshard。它把显存压到最低，但每层参数被 all-gather 了两次（前向一次、反向一次）。
#ShardingStrategy.SHARD_GRAD_OP 梯度+优化器
前向后不 reshard 参数，参数在计算间隙保持完整，只对梯度和优化器状态分片。显存比 FULL_SHARD 高，但省掉了反向前的第二次 all-gather，吞吐通常更好。`NO_SHARD` 退化为 DDP 行为，主要用作调试和对照基线。`HYBRID_SHARD` 则是节点内 FULL_SHARD、节点间复制，适合多机但模型规模不需要跨机全分片的场景，通信量比全局 FULL_SHARD 小。
#ShardingStrategy.HYBRID_SHARD  机内全分片
#ShardingStrategy.NO_SHARD  不分片
============================
# `BackwardPrefetch`
控制反向 all-gather 的预取时机。`BACKWARD_PRE` 在当前参数梯度计算**之前**预取下一组参数，重叠窗口最大，但峰值显存同时持有“当前参数 + 下一组参数 + 当前梯度”；`BACKWARD_POST` 在当前梯度计算**之后**预取，显存更低但重叠更少。
#`MixedPrecision`
 在 FSDP 中需要分别指定 `param_dtype`（前反向计算 dtype）、`reduce_dtype`（梯度 reduce-scatter 的 dtype）、`buffer_dtype`。分片参数在优化器更新和 checkpoint 时保持全精度，只有计算时被 cast 到低精度。把 `reduce_dtype` 设为 `fp32` 可以在低精度计算的同时避免梯度 reduce 的精度损失。
#`CPUOffload`
把参数和梯度在计算间隙移到 CPU，进一步释放 GPU 显存，代价是 PCIe 传输延迟。它适合“显存极度紧张、吞吐可以妥协”的场景；如果开启后吞吐下降超出可接受范围，说明瓶颈已经从容量转移到了带宽。
```

## FSDP2
```python
fully_shard(
    module,
    *,
    mesh: Optional[DeviceMesh] = None,
    reshard_after_forward: Union[bool, int] = True,
    mp_policy: MixedPrecisionPolicy = MixedPrecisionPolicy(),
    offload_policy: OffloadPolicy = OffloadPolicy(),
)

```
### 1. `mesh`：1D 全分片 vs 2D 混合分片（HSDP）

`mesh` 接收一个 `DeviceMesh`。**1D mesh** 是标准的全分片（所有 DP rank 各持有一部分参数）。**2D mesh** 则启用 **HSDP**：一个维度做分片，另一个维度做复制，对应 FSDP1 的 `HYBRID_SHARD`，适合多节点场景——节点内分片、节点间复制，降低跨节点 all-gather 的通信量。

### 2. `reshard_after_forward`：控制前向后的重分片行为

- `True`（默认）：前向后立即释放未分片参数，回到分片状态。对应 **ZeRO-3 / FULL_SHARD** 级别的内存节省。
    
- `False`：前向后保留未分片参数，直到反向结束。对应 **ZeRO-2 / SHARD_GRAD_OP**，以更多显存换更少的重分片通信。
    
- 传入整数（如 `8`）：在每 N 个 Transformer layer 之后重新分片，用于精细调控内存与通信的 trade-off。
    

### 3. `mp_policy`：混合精度策略

通过 `MixedPrecisionPolicy` 控制前向/反向的计算精度和梯度规约精度：
```python
mp_policy = MixedPrecisionPolicy(
    param_dtype=torch.bfloat16,      # 未分片参数在计算中的 dtype，也是 all-gather 的 dtype
    reduce_dtype=torch.float32,      # 梯度 reduce-scatter 的累加精度
    output_dtype=torch.bfloat16,     # 前向输出的 dtype（None 则不转换）
    cast_forward_inputs=True,        # 自动把浮点输入 cast 到 param_dtype
)
fully_shard(model, mp_policy=mp_policy)
```

典型用法是 **BF16 计算 + FP32 梯度规约**：参数在 all-gather 时 cast 到 BF16 以节省通信量，但 reduce-scatter 用 FP32 累加，避免小梯度下溢。

### 4. `offload_policy`：CPU offload
```
CPUOffloadPolicy(pin_memory=True)
```
传入 `CPUOffloadPolicy(pin_memory=True)` 可以把分片参数和梯度 offload 到 CPU，进一步释放 GPU 显存，代价是 H2D/D2H 拷贝开销。较新的版本还支持分阶段 offload 和按预算部分 offload，但基础用法就是全量 offload。

### 5. 显式预取（`set_modules_to_forward_prefetch`）

在包装粒度较细时，默认的 pre-forward hook 触发预取可能偏晚。FSDP2 暴露了手动控制预取的 API，可以在当前模块的 pre-forward 中**提前发出下一个模块的 all-gather**，让计算和通信重叠更稳健。


# 优化器切分ZeRO
切优化器/梯度/参数——解决装不进显存

###  ZeRO-1：切分优化器状态

- **切分内容**：Adam 的 FP32 参数副本 + 一阶动量 + 二阶动量（共 12Ψ12Ψ Bytes）
- **通信模式**：梯度仍需 AllReduce（与 DDP 相同），参数更新后需 AllGather 同步参数
- **显存节省**：每卡从 16Ψ16Ψ 降至 4Ψ+12ΨN4Ψ+N12Ψ​
- **通信量**：与 DDP 相同（2Ψ2Ψ）+ 额外 AllGather 参数
- **适用场景**：优化器状态是显存大头时（Adam 占 75%），少量通信增加换大幅显存节省

### 3. ZeRO-2：进一步切分梯度

- **切分内容**：在 ZeRO-1 基础上，梯度也按分片存储
- **通信模式**：反向传播时使用 ReduceScatter（替代 AllReduce），每卡只保留自己负责分片的聚合梯度
- **显存节省**：每卡降至 2Ψ+14ΨN2Ψ+N14Ψ​
- **通信量**：ReduceScatter = ΨΨ（比 AllReduce 的 2Ψ2Ψ 少一半，但丢失了 AllReduce 隐含的 AllGather）
- **适用场景**：模型中等偏大，切分优化器+梯度后单卡能装下参数

### 4. ZeRO-3：连参数也切分

- **切分内容**：参数、梯度、优化器状态全部切分
- **通信模式**：
    - 前向：AllGather 重组当前层参数 → 计算 → 释放
    - 反向：AllGather 参数 → 计算梯度 → ReduceScatter 梯度 → 释放参数
- **显存节省**：每卡降至 16ΨNN16Ψ​（理想线性缩放）
- **通信量**：3Ψ3Ψ（前向 AllGather ΨΨ + 反向 AllGather ΨΨ + ReduceScatter ΨΨ），比 DDP 多 50%
- **适用场景**：模型参数本身单卡装不下，必须分片

### 5. ZeRO-Offload 与 ZeRO-Infinity

- **ZeRO-Offload**：将优化器状态和梯度计算卸载到 CPU，GPU 只做前向/反向
    - 适用场景：少卡（1-4卡）训练大模型
    - 代价：CPU-GPU 数据传输带宽成为瓶颈（PCIe 4.0: ~32 GB/s）
- **ZeRO-Infinity**：在 Offload 基础上进一步利用 NVMe SSD 存储
    - 适用场景：极大模型（万亿参数）在有限 GPU 上训练
    - 关键技术：分块预取（prefetch）、计算与 I/O 重叠


**zeRO**是论文方面的理论指导
**DeepSpeed (ZeRO)**：由微软开发的**独立库**，是 ZeRO 算法的**原始与参考实现**它提供了最完整的配置选项和功能集。
**FSDP (Fully Sharded Data Parallel)**：PyTorch 的**原生实现**，被普遍视为 **ZeRO-3 风格的 PyTorch 原生版本**。它旨在提供与 DeepSpeed 相当的显存效率，但拥有更简洁的编程模型。

# **流水线并行PP**
## 流水线并行的基本思想

### 朴素实现
```python
stage0: [F.............]
stage1:     [F.............]
stage2:         [F.............]
...
```
任意时刻**只有 1 个 stage 在计算**，其余 p−1p−1 个全部空闲。设备利用率只有 1/p1/p。这就是最朴素的“模型并行”，它几乎没有任何加速价值。[](https://hao-ai-lab.github.io/dsc204a-f25/assets/slides/17.%20mlsys-6.pdf#1#1#1)

流水线并行的基本解法是：把 global batch 切成 mm 个 **micro-batch**，让它们像工厂流水线一样错位流动，使多个 stage 能同时工作。
## GPipe
把一个大Batch切成多个小batch，分批输入进代码之中。
**先全部 Forward，再统一 Backward**
```python
warmup:   F0 F1 F2 ...   （全部 micro-batch 的 forward）
steady:   （无，GPipe 不交错）
cooldown: B0 B1 B2 ...   （全部 micro-batch 的 backward）
```
**优点**：语义最简单，梯度累积干净，实现容易。

**致命缺点——显存 O(m)O(m)**：在“先全 F 再全 B”的模式下，**mm 个 micro-batch 的 activation 必须同时驻留在显存中**，等待后面的 backward 使用。mm 越大（为了压 bubble），activation 显存线性膨胀，很快就把单卡撑爆。

## 1F1B
1F1B 的核心洞察是：**一个 micro-batch 的 forward 完成后，只要它的 backward 被执行，它的 activation 就可以立刻释放**。不需要等所有 micro-batch 的 forward 都做完。
首先模型开始预热
### 真实物理时间线（t=1 到 t=10）

|时间步|S0|S1|S2|S3|说明（F_c 和 F_d 的行踪）|
|---|---|---|---|---|---|
|**t=1**|**F_a**|空闲|空闲|空闲||
|**t=2**|**F_b**|**F_a**|空闲|空闲||
|**t=3**|**F_c**|**F_b**|**F_a**|空闲||
|**t=4**|**F_d**|**F_c**|**F_b**|**F_a**|S0 做完了 `F_d`，此时 S0 存满了 a,b,c,d 四个激活值。S1 处理完了 `F_c`。|
|**t=5**|**空闲(等)**|**F_d**|**F_c**|**B_a**|S1 终于拿到了 `F_d` 开始算；S2 拿到了 `F_c` 开始算；**S3 算完 Loss，立刻开始 `B_a`**。此时 S0 因为存满 4 个，不能做新的 F。|
|**t=6**|**空闲(等)**|**空闲(等)**|**B_a**|**B_b**|**【关键点】** `B_a` 传回 S2，S2 立刻执行 `B_a`。而 `F_d` 本来在 S1 算完了，想传给 S2，但 **S2 正忙着做 `B_a`**，所以 `F_d` 只能在 S1 的通信缓冲区里**排队等待**。同理，S3 在算 `B_b`。|
|**t=7**|**空闲(等)**|**B_a**|**F_d**|**F_c**|**【这里接上了】** `B_a` 传到了 S1，S1 开始算 `B_a`。此时 S2 终于空闲了，立刻把刚才排队的 `F_d` 拿出来算。同时 S3 空闲了，把刚才排队等待的 `F_c` 拿出来算。|
|**t=8**|**B_a**|**F_e**|**B_b**|**F_d**|`B_a` 终于回到 S0，S0 计算 `B_a` 并释放显存！S1 算新的 `F_e`。S2 收到 `B_b` 开始反向。S3 把刚收到的 `F_d` 算完。|
|**t=9**|**F_e**|**B_b**|**F_e**|**B_c**|S0 释放显存后，立刻塞入新的 `F_e`。进入完美的 1F1B 稳态。|
B_a执行完一个阶段后，自动释放掉激活值

## 核心代码实现
```python
from torch.distributed.pipelining import PipelineStage, ScheduleGPipe

# 2. 根据当前rank，构建该阶段对应的子模型
# 例如，总共20层，world_size=2，则rank0拿前10层，rank1拿后10层
full_model = SimpleModel(n_layers=20)
if rank == 0:
    stage_module = nn.Sequential(*full_model.layers[:10])
    # 第一个阶段的输入需要指定，以便分配缓冲区
    stage = PipelineStage(stage_module, rank, world_size, device="cuda",input_args=torch.randn(8, 512).cuda()) 
elif rank == 1:
    stage_module = nn.Sequential(*full_model.layers[10:])
    stage = PipelineStage(stage_module, rank, world_size, device="cuda")
else:
    raise ValueError("This example only supports world_size=2")
# 3. 创建流水线调度器 (例如 GPipe)
# n_microbatches 指定了将batch切分成多少个微批次
n_microbatches = 4
schedule = ScheduleGPipe(  
    stage,  
    n_microbatches=4,  
    loss_fn=criterion,  
)

# 4. 执行一步训练
batch_size = 8

for epoch in range(1):  
    for x, y in dataloader:  
        x = x.to(dev, non_blocking=True)  
        y = y.to(dev, non_blocking=True)  
  
        optimizer.zero_grad()  
  
        if rank == 0:  
            schedule.step(x)          # 只传输入，不在这里碰 loss       
        else:  
            schedule.step(target=y)   # 最后 stage 传 target，loss_fn 内部计算  
  
        optimizer.step()
```

# 混合精度
**混合精度**（用更低位宽算得更快更省）、**梯度累积**（小显存模拟大 batch）、**Activation Checkpointing**（用计算换显存）。它们是把硬件用到极致的基本功。
**计算用低精度，状态用高精度**。

- **数据类型对比**：

|类型|位宽|指数位|尾数位|数值范围|适用场景|
|---|---|---|---|---|---|
|FP32|32|8|23|大|Master weight、优化器|
|FP16|16|5|10|小，易溢出|旧方案|
|BF16|16|8|7|与 FP32 相同|大模型训练首选|
|FP8 (E4M3)|8|4|3|很小|H100+ 的前向计算|

- **为什么混合精度能省显存又提速**：低位宽 → 显存减半 + Tensor Core 算力翻倍
    
- **BF16 混合精度流程**：前向/反向用 BF16 计算，参数更新用 FP32 Master Weight（呼应第3章优化器状态）
    
- **FP16 vs BF16**：FP16 范围小易溢出、BF16 范围同 FP32 但精度低，大模型为何普遍选 BF16
    
- **Loss Scaling**：FP16 训练必须的梯度缩放技巧（静态 / 动态），BF16 因范围大通常不需要
    
- **FP8 训练**：H100 Transformer Engine，前向用 FP8 + per-tensor 动态缩放，反向梯度用 BF16；适用场景与精度风险

## 梯度累积

- **目的**：在有限显存下模拟更大的 Effective Batch Size
- **机制**：连续 KK 步前向+反向累积梯度，每 KK 步做一次参数更新
- **Effective Batch Size** = 单卡 batch × world_size × accumulation_steps
- **与 PP 的配合**：PP 的 micro-batch 本身就实现了类似效果；梯度累积进一步放大
- **与 DDP 的配合**：累积期间用 `no_sync()` 跳过中间步的 AllReduce，省通信
- **注意事项**：Loss 需要除以 KK（或等价地梯度除以 KK）

## 激活重计算

- **问题**：前向保存的激活值随层数和 batch size 线性增长，大模型训练中激活显存可能超过参数显存
- **核心思想**：只保存部分层的激活值（checkpoint），其余层反向时重新前向计算
- **Full Checkpointing**：只保存每个 Transformer Block 的输入，反向时重算整个 Block
    - 显存节省：激活显存从 O(L)O(L) 降至 O(L)O(L​)（每 LL​ 层存一个 checkpoint）
    - 计算代价：约增加 33% 的前向计算量
- **Selective Checkpointing**：只重算计算量小但激活大的操作（如 Attention 的 softmax 输出），保留计算量大的操作的激活
- **配合并行策略**：PP 天然每个 Stage 只需存自己的激活；TP 下 SP 已减少激活冗余（与第6/7章衔接）

## 分发/收集 Scatter/Gather
- **Scatter**：根 rank 把一个大张量切成 NN 份，第 ii 份发给 rank ii（分发）
- **Gather**：每个 rank 把自己的数据交给根 rank，拼成完整张量（收集，Scatter 的逆操作）
```python
dist.scatter(tensor, scatter_list=None, src=0, group=None, async_op=False)
dist.gather(tensor, gather_list=None, dst=0, group=None, async_op=False)

```
